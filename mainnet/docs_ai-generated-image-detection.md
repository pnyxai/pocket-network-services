# `ai-generated-image-detection` — Connection Guide

Canonical connection documentation for the Pocket Network `ai-generated-image-detection` service managed by `PNYX`.
This document is pinned by the service's on-chain card (`specs[0]`).

| | |
|---|---|
| Service ID | `ai-generated-image-detection` |
| Transport | `REST` (HTTP/1.1 and HTTP/2) |
| Expected endpoints | `POST /v1/detect`, `POST /api/v2/task/sync` (Hive-compatible), `GET /readyz` |
| Response determinism | **Variable** — suppliers run different detection models |

> This service scores whether an image was **generated by an AI model**. It returns a probability,
> not a verdict. Deepfake (face manipulation) detection is **not** part of this service.

---

## The API contract

`ai-generated-image-detection` speaks two APIs over the same detector:

- the **image-forensics `/v1/detect` API** — the native surface, and the one new integrations
  should target;
- the **Hive `task/sync` API** — a compatibility layer, so existing Hive clients only swap their
  base URL.

Request and response shapes, field names and error envelopes of both are defined by the
image-forensics OpenAPI 3.1 document, pinned by this service's card (`specs[1]`). Fidelity of the
Hive layer to the vendor is defined by its compatibility notes. We deliberately do not restate all
of it here:

- <https://github.com/RawthiL/image-forensics-service/blob/main/docs/openapi.json>
- <https://github.com/RawthiL/image-forensics-service/blob/main/docs/API_COMPAT.md>
- Upstream Hive reference: <https://docs.thehive.ai/docs/ai-image-and-video-detection>

### What is expected

Three endpoints:

```
POST /v1/detect          # score one image (native)
POST /api/v2/task/sync   # score one image (Hive-compatible)
GET  /readyz             # readiness probe
```

#### `POST /v1/detect`

`POST /v1/detect` accepts `multipart/form-data` with **exactly one** of:

| Field | Type | Notes |
|---|---|---|
| `media` | file | Image upload. JPEG, PNG, WebP, BMP, TIFF, MPO. |
| `media_base64` | string | Alternative to `media`: base64 string or `data:` URI. |
| `url` | string | `http(s)` URL to fetch. **Off by default** on suppliers; do not depend on it. |

A successful response:

```json
{
  "ai_generated": 0.9995,
  "deepfake": null,
  "per_class": {},
  "model_fingerprint": "community-forensics@commfor-384+6076002b…/float16",
  "pipeline_fingerprint": "community-forensics@commfor-384+6076002b…/float16/five+max",
  "crops_scored": 5,
  "elapsed_ms": 41.2
}
```

- `ai_generated` is P(image is AI-generated), aggregated over the crops the supplier's crop
  policy scores.
- `deepfake` and `per_class` are part of the contract but may be `null` / empty; no recommended
  backend fills them.
- Every error is `{"status": "failure", "error": {"type": "…", "message": "…"}}` with a fitting
  HTTP status.

#### `POST /api/v2/task/sync` (Hive)

Same detector, same score, in Hive's envelope. It accepts `multipart/form-data` with `media`
(file) or `url` (off by default, as above). A Hive `Authorization: token …` header is accepted and
ignored.

```json
{"id": "...", "code": 200, "project_id": 0,
 "status": [{"status": {"code": "0", "message": "SUCCESS"},
   "response": {"input": {...},
     "output": [{"time": 0.11, "classes": [
       {"class": "ai_generated", "score": 0.0055},
       {"class": "not_ai_generated", "score": 0.9945},
       {"class": "inconclusive", "score": 0.0055},
       {"class": "none", "score": 0.9945}]}]}}]}
```

- The **generation head** (`ai_generated` / `not_ai_generated`) is the detector's score and its
  complement.
- The **source head** is approximated: a binary detector has no per-generator output, so
  `inconclusive` carries the generated-probability mass and `none` the rest. Do not expect Hive's
  ~80 generator names.
- Not reproduced: the async task API, `algorithmic_tags` (C2PA), video/audio/text submissions and
  every moderation model. `project_id` is always `0`.

### What is not

Everything else. A supplier **MAY** expose `GET /v1/models`, `GET /healthz`, or the Sightengine
compatibility layer (`POST|GET /1.0/check.json`, `models=genai`) — and some will. Consumers **MUST NOT** depend on them. A
supplier MAY also serve `image-container-screening` and `image-prompt-injection-detection` from
the same deployment; those are separate services with separate stakes. Any request outside the
three endpoints above can fail, 404, or behave differently from one supplier to the next, and that
is not a fault — it is the contract.

Note that "expected" is exactly as strong as it sounds. It is the service owner's stated
intention, enforced by no layer of the protocol: nothing checks it at stake time, nothing
checks it at relay time, and a supplier serving only `POST /v1/detect` is a valid supplier
who will be paid normally. Handle a 404 on `GET /readyz` gracefully rather than treating
it as a broken supplier.

## For applications

### Example

```bash
curl -sS "<GATEWAY_URL>/v1/detect" \
  -H "Authorization: Bearer <GATEWAY_API_KEY>" \
  -F "media=@photo.jpg"
```

With a base64 payload instead of a file upload:

```bash
curl -sS "<GATEWAY_URL>/v1/detect" \
  -H "Authorization: Bearer <GATEWAY_API_KEY>" \
  -F "media_base64=$(base64 < photo.jpg | tr -d '\n')"
```

Existing Hive client code works by swapping the base URL:

```bash
curl -sS "<GATEWAY_URL>/api/v2/task/sync" \
  -H "Authorization: Bearer <GATEWAY_API_KEY>" \
  -F "media=@photo.jpg"
```

Use the Pocket application client to talk to the network:

- **<https://github.com/pokt-network/pocket-ap>**

### Results are not comparable across suppliers

This is the single most important thing for an application developer to internalise.

`ai-generated-image-detection` is **model-agnostic**. Suppliers may run Community Forensics or
any other detector that exposes the same `/v1/detect` wire format, with different crop policies.
That means:

- Scores for the same image **differ** between suppliers, sometimes by a lot. A `0.5` threshold
  means something different for each model and crop policy.
- Detectors differ in which generators they catch. One supplier may flag an image another misses.
- You cannot retry across suppliers expecting an equivalent response.
- You cannot cache one supplier's response as another's.
- You cannot cross-check (strictly) suppliers against each other to detect faults.

Every response carries `model_fingerprint` and `pipeline_fingerprint`. Two responses with the same
`pipeline_fingerprint` come from the same weights, precision and crop policy and should agree on
scores. Use it to pin your traffic to a pipeline you have evaluated, or to discard responses from
pipelines you have not.

`results` is `variable` on this service's card for exactly this reason. The only assurance
layer is Pocket Network's crypto-economic incentive: suppliers post stake, are paid for
provably served relays, and are slashed for provable protocol faults. That secures *service
delivery* — that someone answered, in the right wire format — not the quality, calibration,
or accuracy of the model behind the answer.

### Know the limits before you rely on it

- **Modern generators evade current open detectors.** In an independent 2026 benchmark
  ([arXiv:2602.07814](https://arxiv.org/html/2602.07814v1)), Flux Dev, Firefly v4 and Midjourney
  v7 were detected at 18–30% average accuracy across every open method tested.
- **Recompression destroys signal.** Measured on one known-AI image with the recommended model:
  pristine PNG `0.9988` → JPEG q=85 `0.8289` → JPEG q=70 `0.3895`. Send the original file, not a
  re-encoded thumbnail.
- **A low score is not proof of authenticity.** Treat this as one signal among several, never as
  the only one.

If your application needs a known detection rate or false-positive floor, you must measure
it yourself or select suppliers deliberately.

## For suppliers

### Choose a backend

The recommended backend is the PNYX image-forensics service, with `endpoints.detect` and its Hive
layer (`endpoints.detect.compat.hive: true`, the default) enabled:

- **<https://github.com/RawthiL/image-forensics-service>**

It is model-agnostic: the request/response contract stays the same regardless of which detector
you run. Inference can run in-process (ONNX Runtime or torch, CPU or GPU) or on a remote NVIDIA
Triton Inference Server; all runtimes produce identical scores. If you already run Triton for
other services, the `triton` image is the lightest option (no GPU on the service side).

You are free to use any other server, provided it honors the same request and response shapes
for both `POST /v1/detect` and `POST /api/v2/task/sync`, as defined by the OpenAPI document in
`specs[1]`. Do not switch the Hive layer off on a supplier staked for this service.

### Check the license of the model you serve

This service might be seen as a **commercial use** for Pocket Network suppliers. Model weights keep their
own license no matter which server runs them. The recommended Community Forensics weights
(`commfor-384`, `commfor-224`) are **MIT**; their training dataset is CC-BY-4.0 (attribution is
required if you retrain or republish derived weights). Fine-tuned or third-party checkpoints
inherit the license of their base model and training data.

**You are solely responsible for holding the rights to serve the model you deploy.**
Nothing on chain checks the model license.

### No required weights

This service does not mandate specific weights. The recommended starting point is
**Community Forensics `commfor-384`** with the default `five` crop policy and `max` aggregation.
Serve any AI-generation detector that produces `POST /v1/detect` responses in the expected shape.
Be conservative with changes that silently shift behavior: swapping models, precision, or the
crop policy (`center` scores real-world images very differently from `five`) all produce
materially different scores for consumers — and a different `pipeline_fingerprint`.

### Keep URL fetching off

Leave `limits.allow_url_fetch: false` (the default). Fetching image URLs lets any caller make
your node issue requests from its own network position, costs egress, and makes answers depend
on content that can change between suppliers.

### Front it with the HA RelayMiner

Use the high-availability RelayMiner:

### RelayMiner configuration

`ai-generated-image-detection` declares `REST` in its card, which maps directly onto the
RelayMiner config key by lower-casing the on-chain `RPCType` enum name:

```yaml
suppliers:
  - service_id: ai-generated-image-detection
    listen_url: http://0.0.0.0:8545
    service_config:
      backend_url: http://image-forensics:8000
    rpc_type_service_configs:
      rest:                                       # card: {"type": "REST", "intent": "expected"}
        backend_url: http://image-forensics:8000
```


### Verify before you stake

The card ships a healthcheck probe. Run its equivalent against your own stack first — a
failing backend discovered from missed relays is an expensive way to learn:

```bash
curl -sS "http://localhost:8000/readyz" | jq '.endpoints.detect'
# expect HTTP 200 and {"pipeline": "<model fingerprint>/five+max"}
```

Then confirm inference works through the RelayMiner, not just against the
service directly:

```bash
curl -sS "<GATEWAY_URL>/v1/detect" \
  -H "Authorization: Bearer <INFERENCE_API_KEY>" \
  -F "media=@photo.jpg" | jq '{ai_generated, pipeline_fingerprint}'
```

And the Hive layer:

```bash
curl -sS "<GATEWAY_URL>/api/v2/task/sync" \
  -H "Authorization: Bearer <INFERENCE_API_KEY>" \
  -F "media=@photo.jpg" | jq '.status[0].response.output[0].classes'
```

Check that you receive `ai_generated` in the expected shape from both routes before staking.
